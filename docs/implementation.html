02 / IMPLEMENTATION · BASELINE 2.0.0

生成只是一步，
证据才让实现可追溯。

本体不是代码模板的另一种写法。它为转换提供明确输入、为变更提供责任链、为验收提供语义目标；生成器和验证器负责把这套约定落实到特定技术栈。

以下描述仓库中的本地工作台能力。GitHub Pages 仅提供静态说明，不保存项目模型、不运行生成命令，也不提供这里列出的 API。

01 / 从定义到实际结果

OWL + SHACL→ 目录与绑定项目模型→ 校验与批准受限生成→ 观察与验收证据回写
  1. 加载定义：包清单固定本地本体、约束、示例和查询入口；目录以完整 IRI 展示定义、继承和简单 SHACL 关联。
  2. 建立模型：实例引用元模型类型，记录业务意图、设计映射、生成规范与验收目标，并绑定定义版本及摘要。
  3. 检查与规划：先做定义/词汇和模型约束检查；变化通过差异、义务、计划和任务表达。通用差异到完整变更的自动化仍需深化。
  4. 批准并转换：执行受支持的显式转换规则，记录采用的规范、输入与条款，而非让任意描述直接执行。
  5. 采集与验收：记录实际产物摘要，运行验收程序，保存运行结果和证据；实际观察与设计声明分开。
  6. 评估与对账：对指定模型与快照判断满足性，处理义务和就绪范围。输入或产物变化后重新验证证据适用性。

02 / 在工作台完成任务优先级切片

进入本地工作台的「00 元模型中心」。通用模型编辑和已实现的任务优先级切片是两个入口：前者用于建模，后者提供固定范围的真实执行闭环。

A. 查看、建立与检查模型

  1. 按定义包、类型、语义层或关键词查询；打开 BusinessAttribute 或 ValueConstraint，查看完整 IRI、继承、约束和关联来源。
  2. 在「实例与校验」查看任务优先级示例，理解需求、值约束、设计和生成规范的连接。可编辑 Turtle 副本并校验，但不写回原文件。
  3. 使用「关联到当前项目模型」，再进入「02 项目本体」建立类型实例及关系。通用项目草稿目前保存在浏览器 localStorage，不是团队共享模型库。
  4. 运行校验并定位实体、属性路径及错误；覆盖率和影响分析不能当作 dev 满足性证明。

B. 保存并执行受支持的真实切片

  1. 返回「00 元模型中心」，展开「项目实战：任务优先级开发闭环」。输入名称、选择默认值 medium，点击「保存项目模型版本」。
  2. 展开保存的 Turtle，检查需求、条款、设计、生成规范、任务与验收条件。调整默认值后应保存新版本，不覆盖旧版本。
  3. 点击「批准并执行：生成代码 → 运行验收 → 回写证据」。批准绑定当前保存内容，在新的受管理目录生成 src/task.py。
  4. 查看八项固定验收、文件摘要、报告摘要和证据图。该切片的模型与运行历史保存到平台 SQLite；不是写入现有业务仓库。
  5. 点击「重新检查文件与证据摘要」。相关输入、产物、验收文件或定义绑定变化时，当前状态变为 Stale，历史结果保留。

元模型定义本身也可建立草稿、保存修订和执行正反例检查；草稿通过不等于已经安装或发布。导出后仍需要仓库审查，自动发布和迁移未接入。

03 / 生成器读取的是一个有边界的子图

生成规范关联输入作用
appliesRule选择明确实现的 TransformationRule。
inputDesign指定要落实的设计，而不是扫描任意节点猜测代码。
usesTechnology固定技术配置及支持范围。
preserves列明转换必须保留的条款，任务示例包含值约束与既有行为条款。
targetPath指定受检查的输出位置；不是允许写入任意文件。

当前 dev 显式适配器为 python-enum-dataclass-v1。它把受支持的枚举、默认值和非法输入约束转换为 Python 数据类源码。OWL 能表达更多类型，不意味着这个适配器都能生成。

预览会给出源码、输入摘要、转换规则、保留条款及不支持原因。生成规范必须被已批准 ChangePlan 下的 Template 任务采用。写入登记仓库还要求 repositoryId 和显式 overwrite；带 Illustrative 执行记录的示例默认不能写入。

既有 eng 契约模板生成与 dev 生成是两条受区分的路径。包含 dev 术语的模型不能误走旧模板生成器；任意自然语言规则、多技术栈和完整系统生成尚未实现。

04 / 什么才算真实验证？

生成产物→ ObservationRun文件快照→ VerificationRunEvidence→ supportedByEvidence满足性判断

任务切片先移除示例中的 Illustrative 执行和判断，再创建独立的真实执行节点。验收程序不导入生成器，在独立 Python 进程中执行；它不是运行任意程序的安全沙箱。

当前任务切片的八项固定验收，不代表全部业务测试覆盖
输入预期项数
省略优先级得到模型指定的默认值1
low / medium / high各合法值被接受3
未知字符串 / 空字符串 / None / 数字各非法输入被拒绝4

只有固定测试全部通过、前后文件摘要一致且证据图校验通过，才得到这个切片范围内的 Ready。失败时保留报告和 NotSatisfied 判断，义务保持 Open。就绪不包含 API 服务、数据库业务集成或生产发布。

status 表示执行时结论，currentStatus 表示本次读取重新核对后的结论。证据过期后不能沿用历史 Ready；也不能将 Illustrative 演示证据改个名称就当成真实运行。

上述 Python 文件位于仓库 src/code_ontology_platform/。路由由 http_api.py 接入；静态宣传网站与工作台 web/ 独立。

  • ontology/：OWL/Turtle 类型与关系定义。
  • shapes/：SHACL 约束。
  • models/development-metamodel.package.json：定义、约束、示例和查询的本地清单。
  • queries/development/：包内允许的查询，不接受任意客户端 SPARQL。
  • tests/test_metamodel_maturity.py：成熟化约束回归测试。

本体驱动的核心价值，是把“为什么改、改哪里、保留什么、依据什么判断完成”连接起来。扩大能力需要新增明确的词汇、约束、转换器和验收，而不是仅仅增加图上的节点。
