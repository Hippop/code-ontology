01 / MODELING · BASELINE 2.0.0

把需求与代码，
建成有语义的图谱。

建模不是把文档变成一堆节点，而是用稳定的类型、明确的关系和可校验的约束，表达软件为什么存在、如何设计、实际实现了什么。

01 / 先分清定义与实例

层次回答的问题任务优先级示例
元模型定义允许哪些类型与关系？BusinessAttribute、ValueConstraint 和 constrains。
领域扩展特定领域需要哪些专有概念？可设计任务管理领域词汇；领域包的通用安装治理尚未完成。
项目模型这个项目具体要求什么？任务的优先级属性，只允许 low / medium / high。
事实与证据实际代码及验证结果是什么？某次生成的文件摘要、验收执行与报告。

rdf:type 表示项目节点属于某个类型；rdfs:subClassOf 表示类型之间的继承。项目中的“任务概念”也不同于生产数据里的某一条任务记录。

业务属性、接口字段、代码成员和数据库列是不同对象。通过映射说明它们如何对应，不因为名称相同就用 owl:sameAs 合并。

03 / 核心不是节点数量，而是关系语义

目标motivates →需求constrainedBy →契约hasClause →条款constrains →业务概念 / 属性
关键关系；未注明前缀者属于 dev。这里只展示主链，不是全部属性定义。
主语 → 关系 → 宾语它说明什么它不证明什么
Requirement → hasAcceptanceCriterion → AcceptanceCriterion需求如何被验收。验收已经通过。
Requirement → eng:constrainedBy → SemanticContract需求受哪些契约限制。自然语言契约可直接执行。
DesignElement → addresses → Requirement / ContractClause / AcceptanceCriterion设计回应哪些语义目标。代码实现等价于设计。
TechnicalRepresentation → represents → BusinessConcept / BusinessAttribute技术对象表达什么业务含义。两个节点是同一个对象。
RealizationMapping → mappingSource / mappingTarget → 语义源 / 设计或产物显式记录表示、实现、约束落实或验证映射。Declared 声明已经被 Observed 事实确认。
GenerationSpecification → preserves → ContractClause转换必须保留的条款。生成结果自动满足条款。
SemanticDelta → createsObligation → Obligation差异带来实现或验证责任。有任务就等于义务已关闭。
SatisfactionAssessment → supportedByEvidence → Evidence满足性判断的可追溯依据。证据适用于任意版本或整个系统。

设计元素与实际代码产物区分建模；契约条款与执行证据也区分建模。计划中的连接不能冒充观察到的事实。

04 / 案例：为任务增加优先级

业务需求：任务应包含优先级，合法值为 low、medium、high；省略时为 medium；非法输入必须被拒绝。先定义语义，再选择 Python 数据类作为技术表示。

  1. 建立目标和需求：目标解释为什么需要优先级，需求给出范围，验收条件明确默认值、合法值和非法输入处理。
  2. 建立业务概念和属性：Task 是业务概念，priority 是业务属性，两者以 hasAttribute 关联。
  3. 建立约束：ValueConstraint 指向 priority，记录类型、枚举和默认值；既有 BehaviorClause 表达拒绝非法输入的语义。
  4. 建立技术表示和映射：Python Task 数据类及其 priority 字段是设计对象，映射回任务概念和优先级属性。
  5. 准备实施与验收：生成规范引用规则和条款；计划、任务、批准以及验收规范构成受控执行的上下文。
@prefix dev: <https://example.org/code-ontology/development#> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .
@prefix ex: <https://example.org/tutorial/> .

ex:TaskConcept a dev:BusinessConcept ;
    dev:hasAttribute ex:Priority .
ex:Priority a dev:BusinessAttribute .

ex:PriorityValues a dev:ValueConstraint ;
    dev:constrains ex:Priority ;
    dev:valueDatatype xsd:string ;
    dev:allowedValue "low", "medium", "high" ;
    dev:defaultValue "medium" .

这是局部关系示意，省略了模型绑定、身份、版本、契约、计划及证据等必需上下文，不能直接当作完整可执行模型。完整流程见实现页的工作台操作。

05 / 身份、版本和图空间

  • 完整 IRI 标识术语：不同命名空间的同名类型不能合并；旧短 ID 展开后发生碰撞会被拒绝。
  • 业务身份有作用域：同一 ModelRevision 内 canonicalId 必须唯一；不同修订可以保留同一逻辑业务 ID，但使用各自模型节点。
  • 绑定定义版本：metamodelRef 包含定义 ID、版本和内容摘要。旧绑定失效后应导出、重绑、修复并校验，不能只替换摘要冒充迁移。
  • 关系必须处于合法上下文：目标、属性、映射等核心关系受同模型检查；计划义务还必须与目标模型、差异和基线一致。
维度取值用途
graphRoleKnowledge / Change / Impact图承担知识表达、变化表达还是影响分析职责。
graphSpaceCurrent / Business / Desired / Proposed / Approved / Actual / Impact区分当前事实、业务意图、目标、提议、批准与实际结果等上下文。

两个维度正交，不是一条所有图必须依次经过的状态机；它们的存在也不表示已实现通用命名图 Dataset 隔离存储。

06 / 什么样的模型才可继续实施？

OWL/RDFS 描述类型和语义；SHACL 与补充检查验证数据。rdfs:domain / range 具有推理含义，不能替代必填、数量、类型和跨节点一致性的校验。

  • 类型与谓词必须已在保留命名空间内声明，不能靠拼写错误“创建”新术语。
  • 条款目标和映射源必须可解析且类型正确；核心模型关系不得跨修订串接。
  • ValueConstraint 类型来自当前支持词表；默认值必须符合枚举等约束。生成器支持范围可能更窄。
  • 候选定义检查同时运行两个正例与八个关键反例，防止删除约束后“全部通过”。这不是完备的形式化证明。
  • 空图的符合性不等于建模完成；非空普通校验也尚未自动评估全项目完整性。
建模交接清单：定义绑定清楚、需求与验收明确、业务到设计映射可追溯、差异与义务上下文一致、目标转换器明确支持、未解决问题可见。不要用“节点已经画完”代替完整性判断。
